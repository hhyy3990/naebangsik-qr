# 내 방식 QR — Production v3 재게시 직전 DB 마이그레이션 최종 확인

현재 프로젝트는 중앙 접근성 프로필 서비스 **‘내 방식 QR’**입니다.

Development에는 schema v3가 구현되어 있으며, Production은 아직 v2입니다.

데모커피와 무인민원발급기는 공통 SDK v0.5.5를 사용하며 QR v3 모의 응답 테스트를 통과했습니다.

현재 사용자는 Replit의 **‘앱 다시 게시’ 설정 화면**까지 진입했습니다.

확인된 설정:

- 공개 배포
- Autoscale 유형 유지
- Production 데이터베이스 사용
- **‘개발 데이터베이스를 프로덕션 데이터베이스로 복사’ 체크 해제**
- Production DB의 Point-in-Time Recovery 활성화
- 최근 7일 범위의 복원 가능한 날짜·시간 표시
- 예약 일일 백업 비활성화
- 기존 Production 프로필 11개 보존 필요

이번 작업은 **실제 재게시 전에 Production DB에 적용될 변경과 실행 순서를 최종 확인**하는 것입니다.

**절대 Publish 버튼을 누르거나 DB 변경을 실행하지 마세요.**

---

## 1. 현재 Development / Production 상태 재확인

먼저 실제 DB 메타데이터를 읽기 전용으로 확인합니다.

| 항목 | Development | Production |
|---|---|---|
| DB 이름 | heliumdb | neondb |
| schema_version 기본값 | 3 | 2 |
| CHECK 허용값 | 1, 2, 3 | 1, 2 |
| 프로필 수 | 1 | 11 |
| 기존 버전 | v1 | v1 10개, v2 1개 |

값이 달라졌다면 변경된 내용을 보고합니다.

특히 Production 기존 QR 토큰, 프로필 데이터, 관리 코드의 원문은 출력하지 않습니다.

## 2. Replit의 DB 마이그레이션 적용 방식 확인

이번 점검의 가장 중요한 질문입니다.

**사용자가 ‘다시 게시’를 누르면 Development의 DB 스키마 변경이 Production DB에 자동 반영됩니까?**

현재 프로젝트의 Replit 배포 설정과 관리형 데이터베이스 동작을 확인하고, 다음 사항을 구분해 주세요.

A. Replit이 Development → Production 스키마 diff를 자동 적용하는지

B. 사용자가 별도 DB 마이그레이션 승인 단계를 거쳐야 하는지

C. ‘개발 데이터베이스를 프로덕션 데이터베이스로 복사’ 옵션과 스키마 마이그레이션이 서로 독립적인지

D. 체크 해제 상태에서 기존 Production 데이터가 유지되는지

E. schema v3 변경이 코드 배포 전·중·후 어느 시점에 적용되는지

F. Publish 실패 시 DB 스키마 변경도 함께 롤백되는지, 아니면 별도로 복구해야 하는지

G. 실제 Publish 과정에서 사용자가 확인해야 하는 경고나 승인 화면이 있는지

**확인할 수 없는 내용을 자동으로 처리된다고 추정하지 마세요.**

필요하면 현재 Replit의 공식 배포·데이터베이스 문서와 프로젝트 설정을 대조해 주세요.

## 3. 실제 스키마 변경 diff 재확인

이전에 Replit이 제시한 스키마 변경은 다음 세 문장이었습니다.

```sql
ALTER TABLE "profiles"
DROP CONSTRAINT "profiles_schema_version_v2_check";

ALTER TABLE "profiles"
ALTER COLUMN "schema_version" SET DEFAULT 3;

ALTER TABLE "profiles"
ADD CONSTRAINT "profiles_schema_version_v3_check"
CHECK (schema_version = ANY (ARRAY[1, 2, 3]));
```

현재 배포 기준으로 다시 비교합니다.

확인 항목:

- 기존 CHECK 제약의 실제 이름
- 새로운 CHECK 제약 이름
- schema_version 기본값
- v1/v2 데이터가 새 제약을 만족하는지
- 추가 테이블·컬럼 변경 여부
- DROP TABLE 여부
- 기존 데이터 삭제 여부
- 기존 QR token_hash 또는 management_key_hash 변경 여부
- 데이터 초기화 또는 덮어쓰기 여부

**이 세 문장 이외의 변경이 있다면 구체적인 내용과 위험을 보고해 주세요.**

이 SQL은 검토 대상이지 실행 지시가 아닙니다.

## 4. 코드와 스키마 배포 순서 검증

Development v3 서버는 schemaVersion 3 프로필을 생성합니다.

Production DB가 여전히 v2 CHECK 제약을 유지한다면 새 프로필 저장이 실패할 수 있습니다.

따라서 다음을 확인합니다.

- DB 변경이 적용된 후 v3 코드가 요청을 받는지
- 코드와 DB 사이에 일시적인 버전 불일치가 발생할 가능성
- Autoscale 배포에서 기존 인스턴스와 신규 인스턴스가 함께 실행될 가능성
- 구형 서버가 schema_version 3 데이터를 읽을 때의 위험
- 배포 도중 프로필 생성 요청이 실패할 가능성
- 배포 실패 시 구버전으로 돌아가는 방법

필요하면 짧은 점검 시간이나 요청 제한을 제안할 수 있지만, 이번에는 실제 설정을 변경하지 않습니다.

## 5. 백업 및 복원 경로 확인

사용자는 Production DB 설정에서 다음을 확인했습니다.

- 특정 시점 복구 활성화
- 지난 7일 복원 가능
- 복원 가능한 날짜·시간 표시
- 예약 일일 백업은 비활성화

이번에는 다음을 확인합니다.

- 현재 복원 가능한 지점이 마이그레이션 이전 시점을 포함하는지
- Replit의 특정 시점 복구가 스키마 변경도 복원할 수 있는지
- 복원 실행 시 기존 Production 서비스에 어떤 영향이 있는지
- 코드 롤백과 DB 복원을 별도로 진행해야 하는지
- 복구 작업 전에 필요한 사용자 승인 단계

**복원 기능을 실행하거나 백업 설정을 변경하지 마세요.**

## 6. 개발 DB 복사 옵션 검증

현재 사용자는 다음 항목을 체크하지 않았습니다.

‘개발 데이터베이스를 프로덕션 데이터베이스로 복사’

이 설정에 대해 확인합니다.

- 체크 해제 상태에서 기존 11개 Production 프로필이 유지되는지
- 체크 해제여도 스키마 변경만 적용되는지
- 기존 QR 토큰·관리 권한이 유지되는지
- 체크했을 경우 실제 어떤 데이터가 덮어써지는지

**해당 옵션을 활성화하지 마세요.**

기존 11개 프로필과 관리 권한을 유지하는 것이 필수입니다.

## 7. Production 공개 URL 확인

Production URL:

`https://naebangsikqr.replit.app`

현재 `/api/public-config`는 publicAppUrl:null을 반환하지만 공개 웹사이트에서는 window.location.origin으로 QR URL을 생성합니다.

이번 배포에서도 다음을 유지해야 합니다.

- Production 공개 주소 변경 없음
- HTTPS 유지
- Preview 주소로 QR 발급되지 않음
- 기존 v1/v2 토큰 URL 유지
- `/api/profiles/resolve` 정상 응답

이번에는 실제 Production QR을 생성하지 않습니다.

## 8. 배포 직전 코드 검사

현재 Development 상태에서 다음을 확인합니다.

- npm run typecheck
- API 테스트
- npm run build
- v3 프로필 생성·조회
- 하단 60·70·80%
- viewportMode:null
- 기존 v1/v2 정규화
- 프로필 수정·폐기·재발급
- 조회 토큰과 관리 권한 분리

테스트에 쓰기 작업이 필요하면 Production과 격리된 Development 테스트 DB에서만 진행합니다.

기존 Development 프로필과 Production 데이터를 보존합니다.

## 9. 배포 후 검증 계획

실제 Publish는 실행하지 않고 다음 계획을 정리합니다.

1. Production DB schema_version 기본값 3 확인
2. CHECK 허용값 1·2·3 확인
3. 기존 프로필 수 11개 유지 확인
4. 기존 v1/v2 분포 보존 확인
5. 기존 활성 프로필·토큰 보존 확인
6. `/api/health` 정상 확인
7. 공개 웹사이트에 v3 UI 반영 확인
8. v3 테스트 프로필 신규 생성
9. 실제 QR 발급
10. `POST /api/profiles/resolve` 성공 확인
11. 데모커피에서 QR 적용
12. 무인민원발급기에서 동일 QR 적용
13. 설정 변경·재발급·폐기·세션 종료 검증

실제 카메라 스캔과 브라우저 모의 테스트는 구분해 보고합니다.

## 10. 작업 제한

이번 점검에서는 다음을 금지합니다.

- Production Publish 또는 재게시 실행
- Production DB ALTER / INSERT / UPDATE / DELETE
- 수동 마이그레이션 실행
- Production 데이터 초기화
- 개발 DB → Production DB 복사
- 환경변수 변경
- SDK 수정
- 데모커피·무인민원발급기 수정
- 중앙 서비스 URL 변경
- 운영 QR 토큰 폐기·재발급
- 실제 비밀값·토큰 출력

코드 검사를 위한 임시 테스트는 Production과 완전히 분리된 환경에서만 수행합니다.

### 최종 목표

**2. DB 스키마가 v2에서 v3로 정확하게 전환되는가?**
