# 중앙 ‘내 방식 QR’ — 데모커피 연동용 AI API 계약 및 개발 접속 정보 조사

현재 프로젝트는 중앙 ‘내 방식 QR’ Replit입니다.

데모커피 Replit에서 `POST /api/ai-layout/plan` 중계 기능을 구현하려고 하지만 중앙 서버의 정확한 요청·응답 규격과 외부에서 접근 가능한 Development 주소를 확인할 수 없어 안전하게 작업을 보류했습니다.

이번에는 **읽기 전용 조사와 문서 작성만 수행**하세요.

소스코드 수정, 새로운 Mock API 추가, 실제 OpenAI 호출, Secrets 변경, DB 변경, Publish는 하지 마세요.

## 1. 실제 중앙 API 코드 확인

다음 파일을 중심으로 현재 구현을 조사하세요.

- `server/app.ts`
- `server/ai-layout.ts`
- `server/layout-plan.ts`
- `server/layout-policies.ts`
- `server/ai-layout.test.ts`
- `server/AI_LAYOUT_API.md`
- 실제 인증 미들웨어 및 라우트 등록 코드

파일이 이동되었다면 현재 소스의 실제 경로를 사용하세요.

데모커피가 추측 없이 구현할 수 있도록 **실제 코드에 존재하는 정확한 계약**을 추출하세요.

## 2. 요청 계약

다음 사항을 보고하세요.

- 정확한 HTTP 메서드와 경로
- Content-Type
- 실제 요청 JSON의 최상위 필드
- 화면 모델이 들어가는 위치
- `hostId`, `screenId` 전달 방식
- `schemaVersion:2`, `menu.v2` 처리 방식
- 구조·제약 해시 전달 방식
- 화면 크기 및 접근성 제약 전달 방식
- 허용되지 않는 추가 필드 처리
- 최대 요청 크기

**현재 정책 등록에 성공한 데모커피 v2 모델을 기준으로 실제 유효한 요청 JSON 예시 하나를 작성하세요.**

문서에 없거나 소스에서 확인할 수 없는 필드는 임의로 추가하지 마세요.

## 3. 응답 계약

다음 사항을 보고하세요.

- 정상 응답 HTTP 상태 코드
- 정상 응답 JSON의 정확한 구조
- 계획 객체가 들어가는 위치
- `operations` 배열 전달 방식
- 오류 시 HTTP 상태 코드와 JSON 구조
- 인증 실패·정책 불일치·요청 제한·타임아웃 처리
- 오류 메시지에 내부 정보나 민감정보가 노출되지 않는지

데모커피의 `validateMenuLayoutPlan()`이 검사할 수 있는 **실제 정상 응답 JSON 예시**를 작성하세요.

중앙 응답이 별도 envelope로 감싸져 있다면 해당 구조를 반드시 명시하세요.

## 4. 인증 계약

다음을 확인하세요.

- `AI_LAYOUT_SERVICE_TOKEN`의 사용 위치
- Bearer 헤더의 정확한 형식
- 토큰 미설정 시 동작
- 인증 실패 시 상태 코드
- 인증 성공 이후 정책 검증 순서
- 개발·Production 설정 구분

실제 비밀값은 읽거나 출력하지 마세요.

환경 변수의 이름과 설정 필요 여부만 확인하세요.

## 5. 데모커피 v2 정책 확인

현재 중앙 서버에 등록된 `democoffee / cafe.menu / menu.v2` 정책을 확인하세요.

- 화면 모델 버전
- 구조 해시와 검증 규칙
- 제약 해시 재계산 방식
- 세 연산의 대상 및 범위
- 허용·거부 조합
- `compact` / `regular` 제약
- V1~V6 테스트 벡터 결과

데모커피가 생성한 모델을 중앙 API가 실제로 받아들일 수 있는지 **서버 내부 Mock 테스트 기준으로만** 확인하세요.

외부 네트워크 호환성까지 검증했다고 주장하지 마세요.

## 6. 외부 접근 가능한 Development 주소 조사

중요한 부분입니다.

중앙 서비스의 알려진 Production 주소는 다음과 같습니다.

https://naebangsikqr.replit.app

하지만 아직 중앙 AI API는 Production Publish되지 않았습니다.

현재 Replit Development 서버에 **다른 Replit 프로젝트의 서버가 접근할 수 있는지** 확인하세요.

보고할 내용:

- 현재 Development URL
- 해당 URL이 외부에서 접근 가능한지
- Replit 인증·개발 환경 접근 제한 여부
- 별도의 안전한 Preview URL이 있는지
- 요청에 특별한 인증이 추가로 필요한지
- Development URL과 Production URL의 차이
- 외부 접근이 불가능한 경우 가능한 안전한 연결 대안

외부 접속 가능성을 확인하려고 실제 AI API를 호출하지 마세요.

필요하다면 `/api/health` 등 AI를 호출하지 않는 기존 안전한 엔드포인트만 이용하세요.

**실제로 접근을 확인하지 못했다면 ‘접속 미확인’이라고 명시하세요.**

Development 서버가 외부에서 접근할 수 없다면 Production을 임의로 Publish하거나 인증을 우회하지 마세요.

## 7. Mock 통신 경로 확인

현재 중앙 서버에 OpenAI를 호출하지 않고 사용할 수 있는 테스트 경로가 있는지 확인하세요.

- 기존 Mock API 존재 여부
- 테스트 전용 서버 모드 존재 여부
- 외부 서버에서 안전하게 접근 가능한 테스트 경로 존재 여부
- 실제 AI 호출이 일어나지 않음을 보장할 수 있는지

그런 경로가 없다면 **없다고 보고하세요.**

새로운 공개 Mock API를 임의로 구현하지 마세요.

필요하다면 이후 별도 승인을 받아 개발 환경에만 제한된 테스트 경로를 추가하도록 제안하세요.

## 8. 최종 산출물

데모커피 Replit Agent에 그대로 전달할 수 있는 계약 문서를 작성하세요.

문서에는 다음이 있어야 합니다.

1. 실제 요청 JSON 예시
2. 실제 정상 응답 JSON 예시
3. 오류 응답 구조와 상태 코드
4. 인증 헤더 형식

7. OpenAI 없는 Mock 통신 가능 여부
8. 데모커피 중계가 구현해야 할 입력·출력 처리
9. 해결되지 않은 사항
10. 조사 중 코드·Secrets·DB·Production·Publish를 변경하지 않았다는 확인

실제 코드가 길다면 필요한 타입 정의나 함수 부분을 정확히 인용하세요.
