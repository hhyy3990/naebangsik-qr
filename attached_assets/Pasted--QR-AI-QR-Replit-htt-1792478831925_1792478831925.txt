# 중앙 ‘내 방식 QR’ — AI 실시간 키오스크 화면 변환 서버 도입을 위한 최종 사전 조사

현재 프로젝트는 중앙 **‘내 방식 QR’ Replit**입니다.

주소: https://naebangsikqr.replit.app

이번 작업은 **실제 AI가 키오스크 화면의 구성을 결정하고 변경하는 기능**을 구현하기 위한 서버 구조 조사입니다.

**이번에는 읽기 전용 조사만 허용합니다. 소스 수정, DB 변경, 새 API 구현, 외부 AI 호출, Publish는 금지합니다.**

## 1. 개발 목표와 확정된 방향

지금까지 중앙 QR 사이트에서는 AI가 사용자 접근성 설정을 추천하는 기능만 구현돼 있습니다.

이제 다음 기능을 추가하려 합니다.

1. 사용자가 접근성 QR 프로필을 적용합니다.
2. 데모커피 키오스크가 현재 메뉴 화면의 안전한 구조 정보를 생성합니다.
3. 해당 화면 구조와 사용자 접근성 제약을 서버에 전달합니다.
4. OpenAI가 실제로 화면 구성안을 생성합니다.
5. 서버와 SDK가 구성안을 엄격하게 검증합니다.
6. 데모커피 React 앱이 허용된 화면 레이아웃을 실제로 적용합니다.
7. AI 요청 실패 시 기존 화면을 그대로 유지합니다.

**첫 구현 대상은 데모커피의 메뉴 목록 화면 하나입니다.**

예를 들어 기존 2열 메뉴 카드를 AI 판단에 따라 1열 목록형 카드로 변경하는 방식입니다.

이것은 첫 시연을 위한 최소 구현이며 최종 목표는 아닙니다.

이후 메뉴 옵션, 다른 업무 화면, 무인민원발급기, 새로운 키오스크로 확장할 수 있도록 **화면 분석·AI 요청·계획 검증 구조를 재사용 가능하게 설계**하려 합니다.

AI가 미리 정해진 답을 반환하는 가짜 기능이 아니라, **실제 OpenAI API가 화면 정보와 QR 설정을 고려해 구성안을 선택**해야 합니다.

다만 AI가 임의 HTML·CSS·JavaScript를 생성해 실행하는 방식은 허용하지 않습니다.

## 2. 이전 데모커피 SDK 조사 결과

공통 SDK 최신 검증 버전은 `@naebangsik/kiosk-accessibility-sdk@0.5.31`입니다.

데모커피 Agent의 읽기 전용 조사에서 다음이 확인됐습니다.

- SDK `AccessibilityAdapter`가 화면 ID, 버튼, 메뉴, 스크롤 영역, 고정 영역 등을 호스트에서 전달받습니다.
- `screen-change.ts`는 명시적인 단계 변경을 처리합니다.
- `diagnostics.ts`, `layout-enhancements.ts`에는 화면 겹침·크기·잘림 진단 기능이 있습니다.
- QR 프로필 적용과 세션 초기화 기능이 이미 있습니다.
- 하지만 AI용 안전한 화면 의미 모델, AI 응답의 별도 검증기, React 레이아웃 변형 연결 기능은 아직 없습니다.
- 데모커피의 `server.mjs`는 현재 중앙 QR 프로필 조회를 중계합니다.
- 데모커피 저장소에서는 중앙 서버의 OpenAI API·인증·로그 구조를 확인할 수 없었습니다.

따라서 이번에는 중앙 사이트의 실제 서버 코드를 조사해야 합니다.

## 3. 기존 OpenAI Responses API 구조 조사

다음 파일과 실제 연결 관계를 확인하세요.

- `server/recommendation.ts`
- `server/app.ts`
- `server/index.ts`
- 관련 환경 변수·설정 파일
- 관련 테스트 파일

파일 구조가 다르면 실제 경로를 기준으로 조사하세요.

다음 내용을 보고하세요.

- 현재 OpenAI Responses API를 호출하는 함수
- 사용하는 모델과 응답 형식
- 구조화된 JSON 응답 지원 방식
- API 키를 서버에서 보관하는 방법
- `store:false` 적용 여부
- 입력·출력 검증 방식
- 타임아웃 및 실패 처리
- 모델 호출 비용을 유발하는 조건
- 요청·응답 본문이 로그에 남는지
- 기존 AI 설정 추천 기능과 새 AI 화면 변환 기능을 분리하는 가장 안전한 방법

현재 API 키의 실제 값은 출력하지 마세요.

## 4. 중앙 서버에 AI 화면 변환 API를 추가할 수 있는지

추후 다음과 같은 별도 API를 만드는 방안을 검토하세요.

예시:

`POST /api/ai-layout/plan`

이 경로는 조사용 제안이며 이번에는 실제 생성하지 마세요.

예상 입력은 다음과 같습니다.

- 화면 모델 버전
- 호스트 앱 식별자
- 업무 화면 ID
- 화면 구조 버전 또는 구조 해시
- 안전한 요소 ID·역할·그룹·순서
- 허용된 레이아웃 템플릿 목록
- 화면 크기 구간
- 사용자가 선택한 QR 접근성 제약

**실제 입력값, 주문 상태 전체, QR 토큰, 주민등록번호, 이름, 전화번호, 주소, 결제 정보는 보내지 않습니다.**

예상 출력은 다음과 같습니다.

- 선택한 레이아웃 템플릿 ID
- 화면 요소 그룹별 허용된 표시 방식
- 선택 이유를 설명하는 짧은 코드 또는 제한된 설명
- 화면 구조 버전
- 검증 가능한 정형 데이터

AI가 원본 메뉴 항목을 삭제하거나, 가격을 변경하거나, 주문·결제 동작을 변경할 수 없어야 합니다.

다음 질문에 답하세요.

1. 기존 서버 구조에 신규 API를 안전하게 추가할 수 있는가?
2. AI 설정 추천 API와 공유할 수 있는 코드는 무엇인가?
3. 별도의 스키마·검증·프롬프트 파일이 필요한가?
4. 요청량 제한과 서버 인증은 어떻게 구현하는 게 적절한가?
5. 여러 키오스크가 공통으로 사용할 수 있는 API 설계가 가능한가?
6. 초기 시연에 필요한 최소 수정 파일은 무엇인가?

## 5. 데모커피와 중앙 서버의 연결 방식 검토

다음 아키텍처를 우선 검토하세요.

`데모커피 브라우저 → 데모커피 서버 → 중앙 QR 서버 → OpenAI`

중앙 서버가 OpenAI API 키를 보유하고, 데모커피 서버는 중계 역할을 담당하는 구조입니다.

다만 보안·인증·요청량 제한과 개발 환경 연결 가능성을 반드시 검토하세요.

다음 대안도 비교하세요.

- 데모커피 서버가 중앙 AI API를 중계
- 브라우저가 중앙 AI API를 직접 호출
- 별도의 AI 서버 구성

비교할 내용:

- API 키 유출 위험
- 다른 업종 키오스크로 확장 가능성
- CORS 및 인증
- Replit Preview 간 통신
- Production 배포 시 필요한 설정
- 실패 시 기존 화면 유지
- 구현 난이도와 운영 비용

**브라우저나 SDK에 OpenAI 비밀키를 포함하는 방식은 제안하지 마세요.**

## 6. AI 화면 정보의 개인정보 보호

화면 구조를 AI로 전달하는 과정에서 민감정보가 전송되지 않도록 설계하세요.

허용 가능한 데이터는 다음과 같습니다.

- 사전에 정의된 정적 화면 ID
- 의미가 확인된 요소 ID
- 역할과 그룹
- 순서와 상대적 배치
- 화면 크기 구간
- 화면 구조 버전
- 사전에 허용된 템플릿
- 접근성 제약

다음은 전송을 금지합니다.

- input·textarea·select의 현재 값
- 주민등록번호·이름·주소·전화번호
- 결제 정보·주문 상세 상태
- QR 토큰
- DOM 전체 HTML
- 무차별적으로 수집한 `textContent`
- 자유 입력 텍스트
- 호스트 내부 상태 객체 전체

기존 AI 추천 API의 개인정보 보호 정책과 충돌하지 않도록 검토하세요.

요청·응답 본문과 민감한 화면 정보는 로그에 저장하지 않는 방향으로 제안하세요.

## 7. AI 응답 검증과 장애 대응

다음 설계를 검토하세요.

- OpenAI 구조화된 JSON 응답
- 허용한 템플릿 ID만 승인
- 허용한 요소 ID만 참조
- 알 수 없는 필드·예상하지 못한 값 거부
- QR 설정값보다 AI 결과가 우선하지 않도록 처리
- 가격·상품·주문·결제 데이터 불변
- AI 요청 중에도 기존 키오스크 화면 조작 가능
- 응답 지연·타임아웃·실패 시 기존 화면 유지
- 이전 화면에 대한 늦은 결과 무시
- 동일 구조와 설정의 불필요한 반복 호출 방지
- 서버 호출 실패 시 OpenAI 오류 원문을 사용자에게 노출하지 않기

특히 중앙 서버에서 1차 검증하고, 호스트나 SDK에서도 최종 검증하도록 설계할 수 있는지 확인하세요.

## 8. 첫 구현 범위와 확장 가능성

첫 구현에서는 다음만 대상으로 하려 합니다.

**데모커피 메뉴 목록 화면**

- 기존 화면: 2열 카드형
- AI가 선택할 수 있는 예시: 카드형 / 1열 목록형
- 모든 메뉴와 카테고리 유지
- 제품 가격 유지
- 기존 클릭 동작 유지
- QR 접근성 설정 유지
- AI 실패 시 기존 레이아웃 유지

다만 서버 구조 자체는 데모커피에만 하드코딩하지 말고, 추후 다른 호스트와 화면 ID를 지원할 수 있도록 설계해야 합니다.

다음 확장 계획도 제안하세요.

- 메뉴 옵션 화면
- 다른 데모커피 업무 단계
- 무인민원발급기
- 식당 등 신규 키오스크

이번에는 **첫 구현에 필요한 최소한의 서버 구조까지만** 구체적으로 설계하세요.

## 9. 운영 DB·배포 상태 확인

현재 중앙 QR v5는 개발 환경에 구현됐지만 Production에는 아직 Publish하지 않았습니다.

조사할 내용:

- AI 화면 변환 API 구현에 DB 변경이 필요한가?
- 기존 개발 DB와 Production DB에 영향을 주지 않고 구현 가능한가?
- 중앙 QR v5 Publish와 AI API 배포를 한 번에 진행할 수 있는가?
- 별도 인증용 비밀값이 필요한가?
- Replit Secrets 또는 환경 변수 중 추가 설정이 필요한가?

**이번 조사에서 Production DB를 조회·수정하거나 Publish하지 마세요.**

키 이름을 설명하는 것은 허용하지만 실제 비밀값은 출력하지 마세요.
