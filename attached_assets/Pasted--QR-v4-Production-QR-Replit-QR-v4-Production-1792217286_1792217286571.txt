# 내 방식 QR — v4 Production 정식 배포

현재 프로젝트는 **중앙 내 방식 QR Replit**입니다.

사용자가 QR 프로필 v4의 **실제 Production 배포를 승인했습니다.**

이번 작업은 사전 점검에서 확인된 내용을 바탕으로 Production DB 스키마를 v4까지 지원하도록 확장하고, Development에서 완성한 v4 코드를 정식 Publish하는 것입니다.

최종 목표는 사용자가 https://naebangsikqr.replit.app 에서 직접 접근성 설정을 선택하고 QR을 생성한 다음, 데모커피와 무인민원발급기에서 실제 QR을 적용해 보는 것입니다.

**이번 승인 범위를 벗어나는 기능 추가, UI 변경, AI 기능 변경, SDK 수정, 키오스크 수정은 금지합니다.**

## 1. 현재 확인된 상태

Development:
- DB: heliumdb
- 기본 schema_version: 4
- 허용 버전: 1~4
- 기존 프로필: v1 1개, v4 2개

Production:
- DB: neondb
- 기본 schema_version: 3
- 허용 버전: 1~3
- 기존 프로필 11개
- v1 10개: 폐기 상태
- v3 1개: 활성 상태

기존 Production 데이터는 절대 삭제하거나 초기화하지 마세요.

Development의 기존 테스트 QR 2개를 Production으로 복사할 필요도 없습니다.

## 2. Production 백업 및 복구 가능 상태 확인

사용자는 Production DB 백업·복구 기능을 사용할 수 있다고 확인했습니다.

배포 직전 다음을 확인하세요.

1. 실제 Production DB가 neondb인지 확인
2. 복구 가능한 백업 또는 PITR 시점 확인
3. 장애 시 복구 절차 확인
4. 기존 프로필 11개와 활성 프로필 1개를 토큰 노출 없이 집계
5. 배포 전 상태를 기록

백업·복구 기능이 존재하더라도 실제 복구 가능한 시점이 확보됐는지 확인되지 않으면 DB 변경을 진행하지 마세요.

백업을 새로 생성해야 하지만 현재 권한이나 기능으로 수행할 수 없다면 중단하고 보고하세요.

**복구 가능성이 확인된 뒤에만 다음 단계로 진행하세요.**

## 3. Production DB 스키마 v4 확장

사전 점검에서 확인된 DB 차이는 다음 두 가지입니다.

- schema_version 기본값: 3 → 4
- schema_version CHECK 제약: 1~3 허용 → 1~4 허용

v4 설정은 기존 preferences JSONB에 저장되므로 별도 컬럼 추가가 필요하지 않습니다.

Publish 화면이 제시하는 실제 DB schema diff를 확인하세요.

허용되는 변경:

- schema_version 기본값을 4로 변경
- CHECK 제약에 schema_version 4 추가

금지되는 변경:

- profiles 테이블 삭제 또는 재생성
- 기존 레코드 삭제·덮어쓰기
- 기존 v1·v3 프로필 데이터 변환
- 기존 토큰 해시 변경
- 관리 코드 변경
- preferences JSONB 전체 재작성
- 무관한 테이블·컬럼 변경

**실제 schema diff가 예상한 두 변경과 다르면 DB 변경이나 Publish를 실행하지 말고 차이를 보고하세요.**

기존 데이터를 그대로 유지하는 비파괴적 변경만 진행합니다.

## 4. Production v4 Publish

백업과 schema diff가 정상 확인되면 사용자가 승인한 범위 내에서 Production Publish를 진행하세요.

반드시 다음을 확인합니다.

- Development에서 검증된 v4 코드를 배포
- 기존 v1~v3 호환 로직 유지
- 기존 QR 생성·조회·수정·재발급·폐기 기능 유지
- 환경변수·DB 연결 대상 유지
- 새로운 AI 모델이나 프롬프트 적용 금지
- UI 및 접근성 설정 항목의 임의 변경 금지
- Production DB 데이터 보존

배포 중 실패하면 성공으로 보고하지 말고 실패 지점과 복구 필요 여부를 확인하세요.

## 5. Publish 직후 서비스 확인

실제 Production 주소:

https://naebangsikqr.replit.app

다음을 확인하세요.

1. 홈페이지 정상 표시
2. /api/health 정상 응답
3. /api/public-config 정상 응답
4. v4 설정 항목 UI 표시
5. 새 v4 프로필 생성 API 준비 상태
6. QR 조회 API 응답 구조 정상
7. Cache-Control: no-store 유지
8. 기존 v1~v3 호환 코드 유지
9. Production DB의 기존 프로필 11개 보존
10. 기존 활성 v3 프로필 1개 상태 유지

실제 유효한 v3 QR 토큰이 없으면 그 QR의 실제 조회 성공을 확인했다고 보고하지 마세요.

## 6. Production v4 QR 실제 검증

배포 성공 후 Production에서 기존 정상 생성 흐름을 사용해 **v4 테스트 QR 1개만 생성**하고 다시 조회하세요.

테스트 설정은 다음과 같습니다.

- 매우 큰 글씨
- 큰 버튼
- 고대비
- 쉬운 말 켜기
- 스마트 길잡이 켜기
- 하단 조작 사용하지 않음
- 기타 설정은 기존 기본값

QR에 들어 있는 주소는 반드시 다음 Production 호스트를 사용해야 합니다.

https://naebangsikqr.replit.app

확인 사항:

- QR 생성 성공
- 저장된 스키마 버전 4
- 생성 직후 조회 성공
- 모든 설정값 일치
- QR 링크가 Production 주소를 포함
- QR 조회 응답에 no-store 유지
- 기존 활성 v3 QR 상태 유지

검증 결과를 보고할 때 QR 토큰이나 관리 코드를 노출하지 마세요.

사용자가 직접 테스트할 수 있도록 생성된 QR을 확인하는 기존 UI 경로를 알려 주세요.

QR 이미지를 제공할 수 있다면 테스트용 QR 이미지도 전달하세요.

추가 QR은 사용자의 별도 요청 없이 생성하지 마세요.

## 7. 기존 데이터 보존 확인

배포 전후를 비교하세요.

- 기존 프로필 11개가 그대로 존재하는지
- 기존 v1 10개의 폐기 상태가 유지되는지
- 기존 v3 1개의 활성 상태가 유지되는지
- 기존 레코드의 토큰 해시가 변경되지 않았는지
- 기존 프로필의 preferences 데이터가 변경되지 않았는지
- 기존 관리 권한 정보가 변경되지 않았는지

새 v4 테스트 프로필 1개를 생성했다면 Production 총 프로필 수는 12개가 될 수 있습니다.

이 경우 기존 11개와 신규 1개를 구분해서 보고하세요.

## 8. 실제 키오스크 연결 준비

현재 데모커피와 무인민원발급기의 SDK 버전은 v0.5.27입니다.

데모커피의 서버 릴레이는 중앙 Production API를 조회하며, SDK는 Production 주소가 포함된 QR URL을 공식 QR로 인정합니다.

따라서 이번 Production QR을 통해 이전 Development QR 주소 불일치 문제가 해결되는지 사용자가 직접 확인할 예정입니다.

이번 작업에서는 두 키오스크 프로젝트를 변경하지 마세요.

키오스크 연결 성공 여부는 실제 QR을 적용하기 전까지 검증 완료로 표시하지 마세요.

## 9. 중단 조건

다음 상황이 발생하면 즉시 중단하고 보고하세요.

- Production 복구 가능 시점 미확인
- DB diff에 예상하지 못한 삭제·변경 존재
- 기존 데이터 손실 위험
- 실제 DB 연결 대상 불일치
- 기존 v1~v3 QR 호환성 손상 위험
- Publish 과정의 비정상 오류
- v4 생성·조회 실패
- 사용자 승인 범위를 넘어서는 코드 수정 필요

문제를 임의로 해결하기 위해 새로운 기능이나 DB 구조를 추가하지 마세요.
