# 내 방식 QR — Production v3 배포 전 공개 URL·CORS·QR 연결 최종 안전 점검

현재 이 프로젝트는 중앙 접근성 프로필 서비스 **‘내 방식 QR’**입니다.

데모커피와 무인민원발급기에는 공통 SDK `@naebangsik/kiosk-accessibility-sdk@0.5.5`가 적용되어 있으며, QR v3 모의 응답 테스트가 통과했습니다.

중앙 Development에는 schema v3가 구현되어 있지만, 공개 Production 서비스는 현재 v2입니다.

Production DB의 특정 시점 복구(Point-in-Time Recovery)는 켜져 있고 최근 7일 범위에서 복원 가능한 날짜와 시간이 사용자 화면에 표시됨을 확인했습니다. 예약된 일일 백업은 꺼져 있습니다.

이번 작업의 목적은 **Production v3 배포 전 공개 URL·CORS·QR 토큰 조회 경로·두 키오스크의 연결 호환성을 점검하는 것**입니다.

**읽기 전용 점검만 진행합니다. 코드·환경변수·DB·배포 설정을 변경하거나 Publish하지 마세요.**

## 1. 프로젝트와 환경 확인

현재 프로젝트가 중앙 ‘내 방식 QR’인지 확인합니다.

기존에 확인한 환경:

- Development DB: heliumdb
- Production DB: neondb
- Development schema 기본값: 3
- Production schema 기본값: 2
- Production 공개 주소: https://naebangsikqr.replit.app
- Production 프로필 11건 (v1 10건, v2 1건)

실제 현재 상태와 다르면 차이를 보고해 주세요.

환경변수 비밀값과 DB 연결 문자열은 출력하지 않습니다.

## 2. PUBLIC_APP_URL 확인

다음 항목을 조사합니다.

- Development에 PUBLIC_APP_URL 설정이 존재하는지
- Production에 동일 설정 항목이 존재하는지
- Production 런타임에서 실제로 적용되는지
- `/api/public-config`의 publicAppUrl 반환 로직
- 값이 null일 때 window.location.origin을 사용하는 로직
- QR 생성 시 사용되는 최종 URL
- Preview 주소가 Production QR에 섞일 가능성
- HTTPS 및 도메인 대소문자 처리

이전 Production 응답은 다음과 같았습니다.

`{"publicAppUrl":null,"isPreview":false}`

이 응답이 실제 운영 오류인지, 의도된 fallback 동작인지 확인해 주세요.

**Production에서 QR을 만들었을 때 실제 공개 도메인으로 연결되는지 코드와 공개 응답을 이용해 검증합니다.**

실제 프로필을 새로 만들거나 기존 QR 토큰을 출력하지 않습니다.

PUBLIC_APP_URL을 임의로 추가·변경하지 마세요.

## 3. QR 토큰 URL 구조 확인

현재 중앙 QR의 URL 구조는 다음과 같습니다.

`https://naebangsikqr.replit.app/?token=...`

다음 사항을 확인합니다.

- QR에 들어가는 URL 구성 방식
- 호스트와 토큰 파라미터 구조
- 토큰 인코딩 처리
- 토큰 유효성 확인
- 오래된 v1/v2 토큰 URL 호환성
- 폐기된 토큰의 접근 제한
- 브라우저에서 QR URL을 열었을 때의 동작
- 키오스크 SDK에서 토큰을 추출하는 방식과의 계약

실제 Production 토큰은 출력하거나 사용하지 마세요.

토큰 예시가 필요하면 실제 데이터와 무관한 가상의 문자열만 사용합니다.

## 4. CORS 정책 확인

중앙 서버의 실제 CORS 구현을 조사합니다.

확인 사항:

- CORS 미들웨어 또는 응답 헤더 설정
- 허용 Origin 목록
- Development / Production별 차이
- OPTIONS preflight 처리
- POST /api/profiles/resolve의 Origin 검증
- 허용되지 않은 Origin의 오류 처리
- Content-Type: application/json 요청 지원
- Cache-Control: no-store 유지
- 키오스크가 중앙 서버를 직접 호출할 때의 정책
- 키오스크 서버가 프록시로 호출할 때의 정책

**CORS 허용 범위를 편의상 전체 공개(*)로 바꾸지 마세요.**

현재 정책이 보안상 적절한지와 실제 키오스크 연결을 허용하는지는 별도로 평가해 주세요.

## 5. 키오스크 서버 프록시와 중앙 API 경로

현재 두 키오스크는 QR 프로필 조회 시 호스트 서버의 `/api/qr-profile` 엔드포인트를 이용하는 구조로 알려져 있습니다.

중앙 서버의 실제 조회 API는 다음과 같습니다.

`POST /api/profiles/resolve`

요청:

```json
{
  "token": "EXAMPLE_TEST_TOKEN"
}
```

성공 응답의 핵심 구조:

```json
{
  "schemaVersion": 3,
  "preferences": {
    "textSize": "standard",
    "buttonSize": "standard",
    "contrast": "standard",
    "easyLanguage": false,
    "smartGuide": false,
    "guideDelaySeconds": 15,
    "voiceGuidance": false,
    "viewportMode": {
      "mode": "bottom",
      "heightPercent": 70
    }
  },
  "updatedAt": "2026-10-12T00:00:00.000Z"
}
```

다음을 확인합니다.

- 중앙 조회 API가 해당 요청·응답 계약을 유지하는지
- 성공 응답이 SDK v0.5.5의 기대 구조와 일치하는지
- 잘못된 토큰에 대한 404 처리
- 폐기된 토큰에 대한 조회 차단
- 실패 응답에 민감한 정보가 포함되지 않는지
- 서버 간 요청에 브라우저 CORS가 적용되는지
- 프록시 방식에서 필요한 보안 설정

**중앙 프로젝트에 없는 데모커피·무인민원발급기의 코드를 직접 검증했다고 주장하지 마세요.**

소비자 프로젝트 소스가 없다면 중앙 서버 측 계약만 확인하고, 호스트 검증이 별도로 필요하다고 보고해 주세요.

## 6. 비밀정보 및 토큰 보안 점검

다음 사항을 점검합니다.

- Production 비밀키 존재 여부
- 관리 코드 해시 방식
- QR 조회 토큰과 관리 권한 분리
- 조회 토큰으로 프로필 수정·폐기 불가
- 토큰이 서버 로그에 기록될 가능성
- 실패 응답에 토큰이 포함될 가능성
- URL 쿼리 토큰의 브라우저 기록 및 유출 위험
- QR 프로필 조회 시 불필요한 개인정보 노출 여부

실제 키·해시·토큰·연결 문자열의 원문을 출력하지 마세요.

문제가 발견되더라도 이번에는 코드를 변경하지 않습니다.

## 7. 공개 Production 읽기 전용 검증

현재 공개 서비스에서 안전한 GET 또는 무효 토큰 요청만 사용해 확인합니다.

- `/api/health`
- `/api/public-config`
- 공개 프런트엔드의 정적 자산
- 존재하지 않는 가상 토큰에 대한 조회 실패
- 404 및 no-store
- HTTPS 접근
- 서버 오류 여부

실제 Production 프로필을 생성·수정·폐기하거나 실제 토큰을 조회하지 않습니다.

무효 토큰을 이용한 검사는 쓰기 작업이 일어나지 않는다는 것을 코드로 확인한 뒤 수행합니다.

Production에 과도한 요청을 보내지 마세요.

## 8. Development v3 API 검증

Production을 변경하지 않는 범위에서 Development 서버를 확인합니다.

- v3 생성·조회
- viewportMode null
- 하단 60·70·80%
- v1/v2 정규화
- 프로필 수정·폐기·재발급
- 조회 토큰과 관리 권한 분리
- 무효 토큰 오류
- 응답 Cache-Control

테스트 데이터를 생성해야 한다면 Production과 분리된 Development 테스트 환경만 사용합니다.

테스트 후 테스트 데이터를 정리하고 기존 프로필은 보존합니다.

## 9. 배포 직전 점검 항목

Production Publish 화면에서 다음을 확인해야 하는지 정리합니다.

- DB diff가 기존 세 가지 변경만 포함하는지
- 기존 테이블·프로필 보존
- 데이터 덮어쓰기 옵션 비활성화
- 코드·DB 스키마 동시 적용 순서
- PUBLIC_APP_URL 런타임 설정
- CORS 허용 원점
- 서버 시작과 health check
- v3 프런트엔드 정적 번들
- QR 이미지 생성 주소

Replit의 실제 Publish 화면을 확인할 수 있으면 읽기 전용으로 확인하되, Publish 버튼이나 DB 변경 승인 버튼을 누르지 않습니다.
