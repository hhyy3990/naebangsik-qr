# 내 방식 QR — Production v4 배포 직전 사전 점검

현재 프로젝트는 **중앙 내 방식 QR Replit**입니다.

이번 작업의 목적은 Development에서 구현된 QR 프로필 v4를 Production에 안전하게 배포하기 위한 마지막 사전 점검입니다.

사용자는 중앙 QR을 실제 배포한 뒤 데모커피와 무인민원발급기에 연결하여 접근성 설정을 직접 시험하려고 합니다.

**이번 단계에서는 진단과 배포 계획 수립만 수행하세요. 실제 Publish, Production DB 변경, 마이그레이션, 데이터 삭제는 사용자 승인 전까지 절대 실행하지 마세요.**

## 1. 현재 환경 확인

다음 정보를 실제 코드와 환경 설정을 기준으로 확인하세요.

- Development URL과 Production URL
- Development / Production DB의 실제 연결 대상
- 각 DB의 현재 스키마 버전
- v4 관련 코드·마이그레이션 준비 상태
- 현재 Production 배포 버전과 Development 코드의 차이
- 기존 Production QR 조회 API의 정상 동작 여부

현재까지 보고된 정보:

Development:
- DB: heliumdb
- 기본 스키마 버전: v4
- 허용 버전: v1~v4

Production:
- DB: neondb
- 기본 스키마 버전: v3
- 허용 버전: v1~v3
- 기존 프로필 11개: v1 10개, v3 1개

위 정보가 지금도 정확한지 재확인하세요.

## 2. 기존 Production QR 11개 보존

기존 Production 프로필을 읽기 전용으로 점검하세요.

반드시 보장해야 할 사항:

1. 기존 QR 토큰 변경 없음
2. 기존 QR 조회 링크 유지
3. 기존 QR 11개의 데이터 보존
4. 기존 v1·v3 QR 조회 호환성 유지
5. 기존 QR 수정·폐기·재발급 기능 유지
6. QR 조회 권한과 관리 권한의 기존 분리 유지
7. 사용자 개인정보를 새로 수집하지 않음

기존 토큰이나 관리 코드를 보고서에 노출하지 마세요.

실제 운영 데이터 변경 없이 호환성을 검증할 방법을 확인하세요.

## 3. v4 Production 배포 준비 상태

Development에서 구현된 다음 설정들이 Production 배포 코드와 DB에서 정상 처리될 수 있는지 확인하세요.

- textSize
- buttonSize
- contrast
- easyLanguage
- smartGuide
- guideDelaySeconds
- voiceGuidance
- viewportMode
- language
- stepByStepGuidance
- conciseGuidance
- slowGuidance

특히 다음 사항을 점검하세요.

- v4 생성 API가 모든 설정을 정확하게 저장하는지
- v4 조회 API가 모든 설정을 정확하게 반환하는지
- 기존 v1~v3 프로필을 v4 구조로 정규화해 반환하는지
- 지원하지 않는 설정값을 안전하게 거부하는지
- QR 생성·조회·수정·재발급·폐기 과정에서 버전 불일치가 없는지
- v4 프로필 저장에 필요한 Production DB 컬럼이나 제약조건이 있는지
- 코드 배포만으로 충분한지, 별도 DB 마이그레이션이 필요한지

AI 기능은 현재 Development 구현 상태 그대로 유지하세요. 이번 작업에서 AI 기능을 새로 구현하거나 변경하지 마세요.

## 4. Production DB 마이그레이션 사전 점검

Production DB에 변경이 필요하다면 다음을 명확히 보고하세요.

1. 변경이 필요한 테이블·컬럼·제약조건
2. 적용 예정 SQL 또는 마이그레이션 파일
3. 기존 데이터에 미치는 영향
4. 기존 QR 11개의 보존 방법
5. 백업 및 복구 방법
6. 마이그레이션 실패 시 중단 조건
7. 롤백 가능 여부와 한계
8. 마이그레이션과 Publish의 올바른 실행 순서
9. 기존 QR 조회가 중단될 가능성
10. 배포 중 예상되는 서비스 영향

**지금은 마이그레이션 파일을 검토할 수 있지만 Production DB에 실행해서는 안 됩니다.**

백업 완료 여부도 실제 확인 전에는 완료했다고 보고하지 마세요.

## 5. 실제 키오스크 연결 호환성 확인

현재 두 키오스크에서 사용 중인 공통 SDK 버전은 v0.5.27입니다.

데모커피 진단 결과:

- SDK는 Production URL의 QR만 공식 QR로 인식
- 브라우저는 동일 출처의 POST /api/qr-profile 호출
- 데모커피 서버는 Production의 POST /api/profiles/resolve 호출
- Development QR은 SDK의 URL 검증에서 거부될 수 있음
- 브라우저가 중앙 API를 직접 호출하지 않으므로 현재 데모커피 릴레이 구조에서 CORS는 직접적인 장애 요인이 아님

중앙 서비스 관점에서 다음을 확인하세요.

- Production에서 생성하는 QR이 정확히 https://naebangsikqr.replit.app 주소를 포함하는지
- 기존 QR의 URL 형식과 호환되는지
- Production의 /api/profiles/resolve가 v4를 반환할 수 있는지
- v4 응답의 schemaVersion, preferences, updatedAt 형식이 SDK 요구사항과 일치하는지
- 캐시 방지 헤더가 정상 적용되는지
- 실제 Production에서 생성한 QR을 두 키오스크가 조회할 수 있도록 중앙 측에서 추가 조치가 필요한지

별도 프로젝트인 키오스크 내부 코드는 확인할 수 없는 경우 추측하지 말고 미검증으로 표시하세요.

## 6. 배포 후 실제 테스트 계획

배포가 승인되고 완료되면 사용자가 직접 중앙 QR에서 접근성 설정을 선택하고 QR을 생성할 예정입니다.

검증할 항목:

- 하단 조작 없음 / 60% / 70% / 80%
- 기본·큰·매우 큰 글씨
- 기본·큰 버튼
- 일반·고대비
- 쉬운 말 켜기 / 끄기
- 스마트 길잡이 켜기 / 끄기
- 기존 v4의 나머지 설정

같은 QR을 데모커피와 무인민원발급기에서 재사용하여 설정 적용 여부를 확인할 계획입니다.

이번 사전 점검에서는 테스트 QR을 새로 생성하지 마세요.

무인민원발급기에서 발견된 SDK v0.5.27의 하단 80% 긴 설명 약 11px 잘림 문제와 일반 화면의 쉬운 말 안내가 콘텐츠를 가릴 수 있는 문제는 후속 실제 사용성 검증 항목으로 남겨 두세요.

이번 작업에서 SDK나 키오스크 UI를 수정하지 마세요.

## 7. 배포 위험 및 실행 순서 평가

실제 Production 배포를 진행할 때 필요한 작업을 순서대로 제시하세요.

특히 다음을 구분해야 합니다.

- 현재 준비된 작업
- 별도 승인이 필요한 Production DB 변경
- Publish 전에 수행해야 할 검증
- Publish 직후 확인해야 할 기존 QR 호환성
- v4 새 QR 생성·조회 확인
- 장애 발생 시 대응 및 복구 방법

Production 배포가 가능한 상태인지 판단하되, **실제 배포는 실행하지 마세요.**
