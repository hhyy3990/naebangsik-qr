# 중앙 ‘내 방식 QR’ — Replit 개발 서버 간 인증 충돌 해결 및 연결 방식 확정

현재 프로젝트는 중앙 **‘내 방식 QR’ Replit**입니다.

이번 작업은 **데모커피 Replit 서버가 중앙 AI 레이아웃 API에 안전하게 접근할 수 있는 공식적인 방법을 조사하고, 실제 적용 가능한 연결 방식을 제안하는 것**입니다.

**읽기 전용 조사만 진행하세요. 코드 수정, Secrets 생성·변경, Production Publish, 실제 OpenAI 호출은 금지합니다.**

## 1. 현재 개발 상태

중앙 서버:

- `POST /api/ai-layout/plan` 구현
- 데모커피 `menu.v2` 화면 정책 등록 완료
- 구조·제약 해시 검증 구현
- 허용 배치 연산 3개 검증
- V1~V6 Mock 테스트 통과
- 서버 간 인증: `AI_LAYOUT_SERVICE_TOKEN`
- 실제 OpenAI 호출 미실행
- Production Publish 미실행

데모커피 서버:

- `POST /api/ai-layout/plan` 중계 경로 구현
- `server/ai-layout-relay.mjs` 구현
- React 실제 AI 자동 요청 비활성화
- 중앙 응답의 호스트 측 재검증 준비
- 서버 측 `AI_LAYOUT_CENTRAL_URL`, `AI_LAYOUT_SERVICE_TOKEN` 사용
- 중계 기본 비활성화
- 관련 Mock 포함 테스트 87개 통과

현재 중앙 서버는 Development URL을 사용하고 있으며, 해당 주소는 임시 개발 주소입니다.

데모커피와 중앙 QR은 **서로 다른 Replit 프로젝트**입니다.

## 2. 핵심 문제

중앙 Replit Development URL에 접근하려면 Replit External Access Token 인증이 필요할 수 있습니다.

중앙 앱 자체의 인증도 다음 헤더를 요구합니다.

`Authorization: Bearer <AI_LAYOUT_SERVICE_TOKEN>`

문제는 Replit External Access Token 인증도 Bearer 방식이므로, 동일 요청에서 두 인증이 충돌할 수 있다는 것입니다.

**두 토큰을 하나로 합치거나, 확인되지 않은 헤더 형식을 임의로 사용하는 방식은 금지합니다.**

## 3. Replit 공식 지원 방식 조사

Replit 공식 문서를 우선 확인하세요.

- Development URLs  
  https://docs.replit.com/core-concepts/project-editor/app-setup/development-urls

- External Access Tokens  
  https://docs.replit.com/features/deployment-customization/external-access-tokens

다음 질문에 답하세요.

1. 별도 Replit 프로젝트 서버에서 비공개 Development URL에 접근할 수 있는가?
2. External Access Token은 정확히 어느 헤더나 인증 방식으로 전달하는가?
3. 앱 자체의 Authorization Bearer와 동시에 사용할 수 있는 공식 지원 방식이 있는가?
4. 두 Authorization 값이 필요할 경우 중복 헤더·쿠키·별도 헤더 사용을 공식적으로 허용하는가?
5. 외부 접근 토큰에 Development 범위만 부여할 수 있는가?
6. 토큰이 다른 Replit 프로젝트의 서버 환경변수에 있어도 정상 접근 가능한가?
7. Development URL이 변경될 때 어떤 설정을 갱신해야 하는가?
8. 개발 서버를 외부에서 호출할 때 사용량·제한·인증과 관련된 주의사항이 있는가?

**공식 문서에 근거가 없으면 ‘확인되지 않음’이라고 명확히 보고하세요.**

가능하다면 근거 문서의 URL과 해당 설명을 함께 제시하세요.

## 4. 현재 중앙 서버 인증 구조 확인

실제 중앙 서버 코드를 읽고 다음을 확인하세요.

- `AI_LAYOUT_SERVICE_TOKEN` 검사 위치
- `Authorization` 헤더 검사 방식
- 인증이 실행되는 순서
- 서비스 토큰 미설정 시 503 동작
- 인증 불일치 시 401 동작
- `/api/health`의 인증 요구 여부
- `/api/ai-layout/plan`이 실제 OpenAI 호출 없이 종료되는 조건

실제 토큰 값은 절대 출력하거나 기록하지 마세요.

소스에 인증이 필요한 다른 경로가 있다면 그 경로와의 영향도 확인하세요.

## 5. 안전한 연결 방식 비교

다음 방안을 검토하세요.

### A. Development URL의 공식 인증 방법 사용

Replit External Access Token과 중앙 앱 자체의 인증을 동시에 지원할 수 있는지 확인하세요.

지원된다면 **정확한 요청 형식과 필요한 서버 측 설정**을 제시하세요.

### B. 인증을 분리할 수 있는 공식적인 대안

예를 들어 Replit이 제공하는 개발용 외부 접근 기능에 별도의 헤더 또는 다른 지원 인증 수단이 있는지 확인하세요.

공식적으로 지원하는 경우에만 제안하세요.

### C. 별도 제한된 테스트 배포

Development 서버 사이의 연결이 불가능하거나 불확실한 경우, 중앙 QR의 Production과 분리된 **별도 테스트용 배포**를 만드는 것이 적절한지 검토하세요.

이 경우 다음을 설명하세요.

- 기존 Production 서비스와 분리할 수 있는가?
- 개발용 AI API만 안전하게 제공할 수 있는가?
- Bearer 서비스 인증을 유지할 수 있는가?
- 테스트 종료 후 중지·삭제할 수 있는가?
- 유료 배포 비용이나 과금 가능성이 있는가?
- 기존 QR 기능·DB·Production 환경에 영향을 주지 않는가?

**조사 과정에서 새 배포를 실제로 생성하거나 Publish하지 마세요.**

## 6. AI 호출 없는 네트워크 검증 방법

실제 OpenAI API를 호출하지 않고 두 서버의 연결을 확인할 방법을 제안하세요.

가능한 예:

- 인증이 필요 없는 기존 `/api/health`로 순수 네트워크 연결 확인
- 기존 서버에서 지원하는 인증 실패·설정 미완료 응답 확인
- 서버 내부 Mock 테스트
- Replit이 공식 제공하는 접근 확인 기능

단, `/api/ai-layout/plan`에 유효한 인증·유효한 모델을 전달하면 실제 OpenAI 호출로 이어질 수 있습니다.

따라서 **실제 AI 생성기에 도달할 수 있는 요청은 이번에 실행하지 마세요.**

인증 실패를 테스트하는 경우에도 실제 사용 중인 토큰을 출력하거나 노출하지 마세요.

현재 존재하지 않는 새로운 공개 Mock 경로를 임의로 추가하지 마세요.
